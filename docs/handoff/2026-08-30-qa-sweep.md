**Piège d'environnement rencontré (nouveau, à ajouter aux pièges connus)** : v2 et le legacy
nomment tous les deux leur cookie de session `session`, et les cookies ignorent le port. Ouvrir le
legacy sur `localhost:4100` dans le même contexte navigateur **écrase la session v2** (et
réciproquement). Le legacy doit être ouvert dans un contexte isolé
(`new_page … isolatedContext`). Ce n'est pas un bug produit (en production les domaines diffèrent),
c'est une contrainte de la passe QA.

### Bugs trouvés — scénarios et commits

#### Bug #1 — les contraintes HTML natives annulaient silencieusement toute la soumission — `d04d366`

*Reproduction* : `/bookings` → « New booking » → taper `99` dans **Pax nb** → « Create ».
*Avant* : rien. Pas de `POST /api/trips`, aucun message d'erreur, **et les messages de tous les
autres champs obligatoires disparaissaient aussi**. Le bouton avait l'air cassé.

*Cause* : `Pax nb` (`min={1} max={…}`), `Retail net` et `Buffer` (`min={0}`) portaient des
contraintes HTML natives. Le navigateur les évalue **avant** l'événement `submit` : une valeur hors
bornes avorte la soumission entière, `handleSubmit` n'est jamais appelé, et le seul retour est une
bulle native — *en français* dans une application en anglais. La validation appartient au resolver
zod ici (`shouldUseNativeValidation` est off, sa valeur par défaut : vérifié dans la doc RHF).

*Après* : les 3 contraintes passent dans le schéma. `Create` sur un formulaire vide affiche
10 messages lisibles.

#### Bug #2 — messages Zod bruts affichés à l'utilisateur — `d04d366`

*Reproduction* : même chemin, `Create` sur formulaire vide.
*Avant* : « **Too small: expected string to have >=1 characters** » sous Area, et
« Too small/Too big: expected number to be >=1 / <=50 » sous Pax nb. `area` et `paxCount` étaient
les deux seuls champs du schéma sans message ; les internes de Zod arrivaient donc à l'écran.
*Après* : « Area is required. » / « Pax nb must be between 1 and 50. »

#### Bug #3 — la règle « tarif partenaire requis » n'avait nulle part où s'afficher — `d04d366`

*Reproduction* : « New booking » → cocher **Sub-contracted** → « Create ».
*Avant* : le dialogue reste ouvert, aucun message, aucun toast, aucune requête. Le message
« Partner rate net is required to sub-contract a booking. » existait bien dans le schéma
(durcissement acté le 2026-08-29) mais `PriceField` ne rendait **pas de `<FormMessage />`** : les
deux champs de prix étaient les seuls du formulaire sans emplacement pour leurs erreurs.
*Après* : le message s'affiche sous le champ. Idem « A price cannot be negative. » (et un garde-fou
a été ajouté sur `bufferTime`, qui n'en avait nulle part).

Corollaire corrigé dans le même lot : `max={selectedVehicleType.maxPax}` portait, en attribut HTML,
une **vraie règle métier** (`common.js:4327-4331`, portée serveur dans `booking-fields.ts:172`).
Elle est rétablie comme rappel in-app sous le champ, mot pour mot celui du serveur —
« Business accepts a maximum of 3 passengers. » — ce que le legacy faisait aussi, en direct
(`common.js:1033`).

#### Bug #4 — la table affichait le membre d'enum du frais d'annulation — `2791109`

*Reproduction* : `/bookings`, une course annulée avec frais → colonne Status.
*Avant* : « Fee: **FIFTY** ». *Après* : « Fee: 50% », comme le legacy (`common.js:3114`) et comme le
dialogue d'annulation de v2 le disait déjà. Le libellé est désormais partagé entre les deux.

#### Bug #5 — la suite e2e web était rouge depuis le 2026-08-29 — `d04d366`

`auth.setup.ts` échouait en `400 phone must be a valid phone number…` : la passe §15 a rendu `phone`
obligatoire sur `CreateUserDto`, et la fixture `DISPATCHER` (`e2e/config.ts`) n'en a jamais reçu.
Le setup Playwright étant une dépendance de **toutes** les specs, la suite entière ne tournait plus.
Personne ne l'avait rejouée depuis. Le produit a raison, la fixture avait tort : `phone` ajouté.

#### Bug #6 — la validation native du navigateur court-circuitait les messages de l'app — `a231531`

*Reproduction* : `/clients` → « New account » → Create (erreurs affichées) → renseigner First name et
Last name → saisir `not-an-email` dans Email → Create.
*Avant* : le message « First and last name are required… » **restait affiché** alors que les deux
champs étaient remplis, et le seul retour sur l'email était une bulle native en français.

*Cause* : la même que le bug #1, mais d'origine plus large — `<input type="email">` crée une
contrainte native. Le navigateur la vérifie avant l'événement `submit`, la soumission est avortée,
`handleSubmit` ne tourne jamais : rien n'est écrit **ni effacé**, d'où des erreurs périmées.

*Correction* : `noValidate` sur les cinq `<form>` pilotés par un resolver — le dialogue partagé
`record-form-dialog.tsx` (qui sert Clients, Drivers, Vehicles, Bookings, Users), `company-tab.tsx`,
`link-vehicle-to-partner-dialog.tsx` et les deux étapes de `login-page.tsx`. C'est ce qu'attend
react-hook-form, dont `shouldUseNativeValidation` est *opt-in* (vérifié dans sa doc).

## Bugs trouvés pendant les flux — scénarios et commits

#### Bug #10 — un aéroport français sur deux se voyait attribuer l'agent d'assistance de Nice — `41018ab`

**Scénario.** Dialogue « New booking » → PU : taper `CDG`, choisir *Aéroport de Paris-Charles-de-Gaulle,
Tremblay-en-France, France*. Le bandeau sous le champ annonce
« Airport detected — Europe/Paris · **FBO pre-filled (Nice Côte d'Azur (NCE))** » et le champ
`FBO address` se remplit avec *Signature Flight Support **Nice**, …, 06206 Nice*.

**Cause.** `GeoService.fboLookup` comparait ses mots-clés à la requête avec un `includes()` brut,
porté tel quel du legacy (`server.js:1553`). `"nce"` est une sous-chaîne de `"France"` : **toute**
adresse française tombait sur l'entrée Nice du répertoire. Le legacy a exactement le même bug.

**Correction.** Les mots-clés sont maintenant comparés aux **mots** de la requête (découpe sur tout
ce qui n'est ni lettre ni chiffre, en Unicode — `Cannes-Mandelieu` et `Genève` continuent de
matcher). v2 diverge du legacy en connaissance de cause.

**Rouge d'abord.** Test unitaire ajouté sur `fboLookup` (3 cas : match par nom/code, non-match dans
un mot plus long, aéroport hors répertoire) → `● GeoService › fboLookup › does not match a keyword
buried inside a longer word`, 1 échec sur 14. Vert après correction, puis **revérifié dans le
navigateur** : `fbo-lookup` renvoie `found:false` sur CDG et continue de répondre juste sur Nice,
Genève et Le Bourget.

#### Bug #11 — une course d'aéroport rouverte cachait tout son bloc « Flight info » — `2861853`

**Scénario.** Créer une course dont le PU est un aéroport que le géocodeur ne sait pas nommer par
son code IATA — *Aéroport de Nice-Côte d'Azur* en est un —, renseigner l'adresse FBO, enregistrer,
puis **rouvrir la course en édition** : les champs `Flight number`, `Buffer (min)`, `FBO address`,
`Tail nbr` et `Nameboard` ont disparu. La course les porte toujours en base (rien n'est perdu à
l'enregistrement), mais ils sont devenus **invisibles et non modifiables**.

**Cause.** `pickupIsAirport` est un champ *de formulaire* alimenté par l'appel de géocodage ; il
n'existe plus quand le dialogue se rouvre sur une course enregistrée. `showAirportInfo` retombait
alors sur le seul code IATA — exactement le cas que son propre commentaire dit vouloir couvrir
(« geocoding recognises an airport more often than it can name one »).

**Correction.** `showAirportInfo` s'ouvre aussi sur ce que la course **porte déjà** : un numéro de
vol, un buffer, une adresse FBO, un tail number ou un nameboard. Dérivé de la course, pas des
valeurs courantes du formulaire — sinon vider le champ FBO refermerait le bloc sous les doigts de
l'utilisateur.

**Rouge d'abord.** 2 tests ajoutés à `trip-form-rules.test.ts` → `× keeps it open on a saved
booking that carries flight data but no code`, 1 échec sur 25. Vert après correction, et le bloc
réapparaît à l'écran sur la course de test.

#### Bug #12 — chaque toast s'affichait deux fois — `2861853`

**Scénario.** Créer un compte : le toast « Account CI22 created. » apparaît **dans deux régions
`aria-live` distinctes**. Les lecteurs d'écran l'annoncent donc deux fois.

**Cause.** `<Toaster />` était monté deux fois : dans `App.tsx` et de nouveau dans `AppShell`.

**Correction.** Celui de `AppShell` est retiré ; celui de `App` couvre aussi `/login` et les pages
publiques.

**Rouge d'abord — par sabotage.** Les trois specs Playwright qui lisent des toasts contournaient le
symptôme avec `.first()` et une explication fausse (« sonner renders each toast twice (visible +
aria-live announcer copy) »). Elles assertent désormais **un seul nœud** (`a04b946`). Sabotage
appliqué : `<Toaster />` remis dans `AppShell` → `client-lifecycle.spec.ts` échoue avec
*« strict mode violation: … resolved to 2 elements »*, les deux portant « Account CC2 created. ».
Sabotage retiré → 3 specs vertes. Un `MutationObserver` posé dans le navigateur confirme qu'après
correction **un seul** nœud `[data-sonner-toast]` porte le texte.

*Note :* la boucle d'avancement de statut de `booking-lifecycle.spec.ts` garde volontairement un
matcher souple (`.last()`) — deux étapes consécutives lèvent la **même** phrase et le toast
précédent est encore à l'écran. La raison est écrite dans le fichier.

#### Bug #13 — un partenaire enregistré comme société sans personne nommée était une ligne vide — `fe92650`

**Scénario.** Ouvrir le sélecteur `Driver` d'une course : deux options s'affichent comme
` (D-XX-XX-MAN-001)` et ` (D-XX-XX-UBE-001)` — un espace, puis une référence. Idem dans le filtre
`Driver` de `/bookings`, où elles apparaissent comme deux lignes **entièrement vides**, donc
impossibles à lire, à taper ou à choisir.

**Cause.** Les deux sélecteurs libellaient leurs options avec le champ `name` calculé par l'API,
qui est `prénom + nom` — vide sur un enregistrement de partenaire qui n'est qu'une société. La base
de dev en contient deux (`Manual Test Partners`, `Uber`).

**Correction.** `driverLabel` (`@cockpit/shared`) existe **exactement pour ça** — son commentaire le
dit : « so that a nameless partner company still reads as something in a toast, a table cell or a
picker » — et n'était pas appelé. Un `driverOptionLabel` l'enveloppe avec la référence, et le
pré-remplissage « New booking » depuis une ligne de `/drivers` s'en sert aussi au lieu de répéter le
même gabarit.

**Rouge d'abord.** Helper d'abord écrit dans sa forme buggée, avec 3 tests → 2 échecs
(`× falls back to the company…`, `× falls back to the ref alone…`), puis corrigé. Vérifié à
l'écran : le filtre `Driver` liste désormais `Manual Test Partners`, `Marco Rossi`, `Uber`, `Léa
Fontaine`, `James Whitfield`, `Julien Petit`, `Karim Haddad`.

#### Bug #14 — on pouvait sous-traiter une course sans dire à qui — `56609c9`

**Scénario.** Dialogue « New booking » → cocher `Sub-contracted`, saisir un tarif partenaire, ne
**pas** choisir de partenaire → `Create` passe. La course est alors confiée à personne : le serveur
la fige à `Sent` (`decideAssignment` : `locked = subContractor && !partnerId`), le bouton d'envoi
n'est jamais réarmé, et elle reste dans la liste avec l'air d'être partie.

**Cause.** Le schéma du formulaire exigeait le **tarif** partenaire mais pas la **société**. Le
legacy gardait son bouton de soumission grisé tant que le champ Partner était vide
(`refreshFormGuards`, `common.js:1046-1054`) ; ce garde est tombé avec les popups d'édition rapide
non portées. Le champ `Partner` n'avait pas non plus de `<FormMessage/>` — même forme que le bug #6.

**Correction.** `partnerRef` requis dès que `subContractor` est coché, message
« Partner company is required to sub-contract a booking. », marqueur `*` sur le libellé et
`<FormMessage/>` ajouté.

**Rouge d'abord.** 3 tests ajoutés à `trip-form-schema.test.ts` → 2 échecs
(`× rejects a sub-contracted booking with no partner company`, `× rejects a partner company that is
only whitespace`). Un test existant (« accepts a sub-contracted booking once a rate is given »)
**a dû être complété** d'un `partnerRef` : il affirmait une règle incomplète. Vérifié à l'écran : le
message s'affiche sous le champ, à côté de celui du tarif.

#### Bug #15 — un partenaire société disparaissait des pages publiques et des messages au POC — `df33a51`

**Scénario.** Confier une course au partenaire `Uber` (société sans chauffeur nommé), puis ouvrir
`/track/<ref>` : la ligne **Driver** affiche « **To be confirmed** » alors que la course est bel et
bien assignée. Le message WhatsApp envoyé au POC sort en « this is **, the driver** ».

**Cause.** Même racine que le bug #13, côté API cette fois : `toPublicTrip` et
`buildTripMessageContext` composaient le nom de l'assigné avec `driverDisplayName` (prénom + nom),
vide sur ce type d'enregistrement.

**Correction.** Les deux utilisent `driverLabel` (nom → société → ref) ; les formes étroites
`driver`/`partner` transportent désormais le `ref` et la `company` dont il a besoin.

**Rouge d'abord.** `public-trip.mapper.ts` **n'avait aucun spec** — il en a un (5 cas, dont la
redaction POC/instructions entre la vue chauffeur et la vue passager). Les deux specs ont donné
`● toPublicTrip › falls back to the partner company when nobody is named on it` puis
`● buildTripMessageContext › falls back to the partner company when nobody is named on it`, 1 échec
chacun. Vert après correction, et `/track/R-CC1-26-1` affiche maintenant « Driver — Uber ».

## Ce qui n'a pas pu être testé

- **Le contenu des fichiers exportés** (Excel client, Excel log partenaire, PDF de facture) : le
  navigateur d'automatisation n'écrit pas les téléchargements sur disque. Les trois exports sont
  couverts par `invoicing-lifecycle.spec.ts`, qui attend l'événement `download` et vérifie les noms
  de fichiers.
- **L'envoi réel des messages WhatsApp** : Twilio n'est pas configuré en dev. Le corps composé est
  loggé par l'API et a été relu à chaque étape du flux §5 — c'est le contenu qui a été vérifié, pas
  l'acheminement.
- **Les brouillons d'email** (`mailto:`) : l'ouverture du client mail est un passage de relais au
  système. Ce qui a été vérifié, c'est la **réponse serveur** qui les alimente — destinataire,
  sujet, corps — recoupée avec le gabarit legacy.
- **Le mode `tracking: false`** de la page chauffeur : non exercé à l'écran (aucune course de dev ne
  l'a désactivé). Vérifié par lecture croisée du code legacy et v2, et couvert par
  `public-trip-lifecycle.spec.ts`.
- **Le vrai `offerEventReactivation`** : la feature n'existe pas en v2 (documentée dans le rapport
  d'écarts). Ce qui a été testé, c'est ce que v2 offre à la place — la relance manuelle par
  extension des dates de l'événement, qui fonctionne.
