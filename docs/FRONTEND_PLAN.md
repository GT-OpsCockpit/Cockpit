# Cockpit v2 — Plan Frontend (React + TypeScript + Tailwind)

> Document vivant : la section "État actuel" ci-dessous est la version en vigueur. Tout changement de cap s'ajoute au **Journal** en bas du fichier, jamais en réécrivant l'historique.

## État actuel

### Contexte de décision

Issu d'une session de cadrage (2026-08-26) : le choix exact entre React/Vue a été délégué ("peu importe, là où tu as le plus de références"), avec une exigence ferme : **Tailwind CSS**. SSE retenu pour le temps réel (fin du polling 5s du legacy). Voir `LEGACY_FEATURES.md` §10 pour l'inventaire complet des pages/comportements à reproduire.

### Stack

- **Monorepo pnpm** : `apps/web` (Vite + React + TypeScript + Tailwind), partage de types/schémas Zod avec `apps/api` via `packages/shared`.
- **UI kit** : Tailwind + shadcn/ui (composants Radix headless stylés Tailwind).
- **Routing** : React Router.
- **Data fetching/cache** : TanStack Query.
- **Formulaires** : React Hook Form + Zod (schémas partagés avec les DTOs NestJS via `packages/shared`).
- **Temps réel** : hook `useTripEvents()` sur un flux SSE (`/api/events/stream`), invalide le cache TanStack Query correspondant à la réception d'un événement.

### Pages (mappées depuis l'inventaire legacy)

Authentifiées :
- `/login` — email+mot de passe puis code 2FA (un compte par utilisateur, plus un seul compte admin partagé comme au legacy).
- `/bookings` (ex-`dispatcher.html`) — barre de création de course + listes Local/Farm out.
- `/clients`, `/drivers`, `/vehicles` — CRUD + popups d'édition/indisponibilité, mêmes règles conditionnelles que le legacy.
- `/planning` — toggle chauffeurs/véhicules, vue liste + vue timeline Gantt drag&drop.
- `/events` — sélection/création de compte événement + "Create bulk".
- `/invoicing` — onglets Customer/Driver log/Partner log/History.
- `/finance` — stub (fidèle au legacy, qui n'a jamais eu de logique ici non plus).
- `/settings` (ex-`owner.html`) — infos société + gestion des utilisateurs (remplace le panneau "Access" décoratif du legacy par une vraie gestion de comptes).

Publiques (sans auth, comme le legacy) :
- `/driver/:ref` (ex-`chauffeur.html`) — page mobile chauffeur, 5 boutons d'étape.
- `/track/:ref` (ex-`dashboard.html`) — suivi client en lecture seule, **SSE au lieu de polling 5s**.

### Composants partagés à recréer (équivalents `common.js`)

- Combobox recherche (pays, référence client/chauffeur, POC, adresse via géocodage).
- `RecordDialog` — popup générique d'édition/création (remplace `openRecordModal`).
- Popup de confirmation générique.
- Timeline Gantt réutilisable (planning chauffeurs/véhicules), drag&drop d'assignation.
- Hint devise/FX (taux de change live).
- Popup infos vol (vérification FlightStats).
- Popups indisponibilité chauffeur/véhicule.

### Branding

Réutilisation des assets existants (`cockpit-icon.webp`, `cockpit-wordmark.png`), palette verte "WhatsApp" du legacy comme point de départ (`--green:#128C7E`), adaptée en tokens Tailwind (`theme.extend.colors`).

## Journal

> **2026-08-26 — Version initiale.** Issue de la session de cadrage (grilling) : React + TypeScript + Tailwind (choix du framework délégué, Tailwind imposé), monorepo pnpm partagé avec le backend, SSE pour remplacer le polling 5s legacy, pages mappées 1:1 depuis l'inventaire `LEGACY_FEATURES.md`.

> **2026-08-26 — Lancement de l'implémentation (grilling #2).** Le back (`apps/api`) est déjà largement implémenté (Auth/Users/Company/Meta/Clients/Drivers/Fleet/Notifications/Geo/Trips/Invoices/Realtime, tous testés e2e) ; `apps/web` était encore un scaffold Vite par défaut. Décisions de cadrage avant de coder :
> - **Ordre** : verticale complète d'abord (`/login` + `/bookings`, page la plus centrale du legacy `dispatcher.html`) plutôt qu'un scaffold en largeur de toutes les pages. Les autres pages authentifiées/publiques suivront en itérations séparées.
> - **Partage de types front/back** : le back utilise `class-validator` (pas Zod) et n'exposait aucun OpenAPI. Ajout de `@nestjs/swagger` sur les DTOs existants (non-invasif) + génération d'un client typé dans `packages/shared`, plutôt que des types dupliqués à la main ou rien de partagé — élimine le risque de dérive.
> - **Ajouts back additifs** décidés pour débloquer le front : `GET /api/auth/me` (identité + rôle courant, absent jusqu'ici, nécessaire pour le nav rôle-gated) et un provider WhatsApp "dev" (log console) sélectionné automatiquement quand `TWILIO_ACCOUNT_SID`/`TWILIO_AUTH_TOKEN` sont absents — sans ça, Dispatch/Notify/Advance-step (qui appellent `TwilioWhatsAppProvider`, codé en dur, sans fallback) seraient impossibles à tester en local.
> - **Données de test** : `prisma/seed-data.ts` étendu avec des clients/chauffeurs/véhicules flotte d'exemple (le seed actuel ne créait que l'admin + pays + types de véhicule ; le formulaire de course n'autorise aucune création à la volée).
> - **Fidélité legacy** : comportement/règles métier reproduits fidèlement (voir `LEGACY_FEATURES.md`), UI entièrement redessinée en shadcn/ui (pas de copie pixel du CSS artisanal legacy), accent vert de marque (`#128C7E`) conservé.
> - **Périmètre de la verticale bookings** : tout inclus dès cette passe — barre de création, tableaux Local/Farm out + filtres, popups d'édition rapide, annulation avec mot de passe manager (vérifie le mot de passe de l'utilisateur courant via `verify-password`, plus un secret partagé unique comme au legacy), dispatch-driver + advance-step (workflow de statut complet), upload nameboard, popup vérif vol (FlightStats, dégradé proprement si non configuré) et hint FX/marge live.
> - **Tests** : suite complète Vitest + Testing Library sur la logique à risque (règles de validation conditionnelles, machine à états du workflow de statut) + Playwright e2e sur le parcours création→dispatch→statuts, au même niveau de rigueur que les tests e2e déjà en place côté back.
> - **Dev workflow** : stack `docker compose up` (Postgres+api+web) utilisée pendant toute l'implémentation, vérification systématique au navigateur (pas seulement via les tests) avant de considérer un écran terminé.

> **2026-08-27 — Verticale Clients close, décision d'architecture pour les listes.** `/clients` terminé au même niveau de rigueur que Bookings (voir `docs/handoff/2026-08-27-frontend-clients-2.md`). Décision de cadrage explicite de l'utilisateur pendant cette session, applicable à toutes les verticales restantes (Drivers, Vehicles) : **ne pas répliquer les mauvais patterns techniques du legacy sous prétexte de fidélité** — la fidélité au legacy s'applique à la logique métier (règles de validation, calculs), pas à ses choix d'implémentation. Flaggé concrètement : `ClientsService.list()`/`DriversService.list()` (`findMany()` sans pagination ni filtre serveur, tout le filtrage côté front) reproduit tel quel le pattern legacy (`clients.html`/`drivers.html`) — accepté pour l'instant afin de ne pas bloquer la clôture de Clients, mais **à refondre en pagination/filtre serveur** avant de considérer l'architecture de liste comme définitive. Vérifier ce même piège avant de démarrer Drivers/Vehicles.

> **2026-08-27 — Pagination serveur + email validation/dedup, même session.** Revirement immédiat de la décision "on diffère" ci-dessus — traité dans la foulée plutôt que reporté (voir `docs/handoff/2026-08-27-frontend-clients-3.md`). `GET /api/clients` prend maintenant `search`/`type`/`includeInactive`/`page`/`limit` et renvoie une enveloppe paginée ; `page`/`limit` restent opt-in pour ne pas casser le combobox client de Bookings (qui a légitimement besoin du roster complet, comme le combobox pays). Email : format + déduplication (insensible à la casse) sur le champ `email`, format seul sur `pocEmail`, une seule implémentation (`packages/shared/src/validation/email.js`, réutilisée telle quelle par le schema Zod front et `ClientsService` back — pas de logique dupliquée). `DriversService.list()`/`FleetVehiclesService` gardent le même problème non résolu, à traiter à leur tour.

> **2026-08-27 — "Plus rien sans pagination" : le compromis opt-in ci-dessus est rejeté.** L'utilisateur refuse le mode "si `page`/`limit` sont omis, tout renvoyer" posé juste au-dessus pour le picker Bookings (voir `docs/handoff/2026-08-27-frontend-clients-4.md`) : **aucun endpoint de liste ne doit fonctionner sans borne**, quel que soit le cas d'usage — le bon pattern dépend du cas, pas une exemption. Pickers/dropdowns (Customer/Driver/Partner/Reg Nbr, filtres Bookings) passent en **request-on-demand** (recherche distante bornée, `useOptionMemory`+`SearchCombobox`) plutôt qu'en pagination classique — un combobox n'a pas besoin d'un tableau paginé. Le tableau Bookings (live, refresh SSE) passe à une **fenêtre de dates résolue côté serveur** (`period=upcoming/today/week/past/all`), reproduisant la règle `baseVisibility` qui était dupliquée côté front. `Drivers`/`FleetVehicles` reçoivent au passage le même traitement pagination/filtre que Clients (jusque-là aucun des deux n'avait ni l'un ni l'autre).

> **2026-08-27 — Verticale Drivers close.** `/drivers` construit au même niveau de rigueur que Clients (voir `docs/handoff/2026-08-27-frontend-drivers.md`) : deux tableaux Chauffeurs/Partenaires depuis la réponse paginée du back, validation conditionnelle miroir de `assertValidDriverFields()`, sélecteur d'Événement request-on-demand pour les chauffeurs `eventsOnly`, popup d'indisponibilité type-verrouillé, nouvelle permission `driver:reactivate` (suggérée par `docs/agents/permissions.md`, jusque-là non câblée). `ListPagination` extrait en composant partagé (`apps/web/src/components/list-pagination.tsx`) — Clients et Drivers l'utilisent tous les deux, plus de duplication. > **2026-08-27 — Verticale Vehicles (Fleet) close.** `/vehicles` construit au même niveau de rigueur que Clients/Drivers (voir `docs/handoff/2026-08-27-frontend-vehicles.md`) : deux tableaux Internal/External **à colonnes différentes** (contrairement à Drivers), Nb Pax jamais éditable (recalculé côté client via `defaultFleetPax()`, porté du legacy), nouvelle permission `vehicle:reactivate`, et le popup de liaison véhicule↔partenaire différé par la session Drivers (câblé depuis `DriverCreateDialog` via une case "Ind." ou une confirmation Oui/Non pour les chauffeurs `eventsOnly`+Company). À retenir pour tout futur `<Select>` en cascade. Reporté, hors périmètre : le padlock "délier ce véhicule" côté Drivers (nécessiterait une nouvelle relation inverse `DriverEntity.fleetVehicle`).

> **2026-08-27 — Pages publiques `/driver/:ref` et `/track/:ref` closes, vraie fuite de données publique trouvée et corrigée au passage.** Voir `docs/handoff/2026-08-27-frontend-public-tracking.md`. Choix laissé à l'agent entre ces deux pages et le stub `/finance` — tranché en faveur de celles-ci après qu'un état des lieux a révélé que `GET /api/trips/:ref` et `POST /api/trips/:ref/notify` (déjà `@Public()` depuis la verticale Trips, jamais consommés côté front avant cette session) renvoyaient la `TripEntity` complète sans projection — prix, VAT, email/téléphone chauffeur+partenaire accessibles à quiconque tient un lien `ref`, sans authentification, contrairement au legacy dont le back pré-formatait une réponse minimale pour ces deux pages précises. Corrigé via une nouvelle `PublicTripEntity`/`toPublicTrip()` (mapper pur, `apps/api/src/trips/public-trip.mapper.ts`) : POC/instructions visibles seulement en vue chauffeur, jamais de prix/`client`/`driver` bruts dans aucune des deux vues. `GET /api/events/stream` (SSE, déjà construit pour Bookings) passé `@Public()` aussi — payload sans donnée sensible, juste jamais rendu public faute de consommateur avant. **Deuxième bug trouvé et corrigé pendant la vérification navigateur** (pas dans le scope initial) : l'auto-stamp TRANSMITTED/RECEIVED de `getPublic()` n'était pas idempotent — deux ouvertures quasi simultanées du lien chauffeur (React StrictMode en dev le déclenche de façon fiable) pouvaient toutes les deux tenter d'insérer le même `TripStep`, `@@unique([tripId, step])` faisant échouer la perdante en 500 brute. Fix d'une ligne (`skipDuplicates: true`), repéré en observant une vraie 500 dans les devtools réseau pendant la vérification, pas en lisant le code. Écart delibéré supplémentaire, identifié dans la foulée : ces deux pages activent un `retry` sur leur query (`retryPublicQuery`, `apps/web/src/features/public-tracking/`) contrairement au `retry:false` global de l'app — sans login à rediriger en cas d'échec, une page publique qui abandonne après un seul aléa réseau est *moins* robuste que le polling bête du legacy qu'elle remplace.
